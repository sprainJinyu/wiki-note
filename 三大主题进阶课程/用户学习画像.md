# 用户学习画像（JMM 相关）

> 基于对话中观察的思考习惯、思路特点与学习方式，仅做客观记录。

## 思考习惯

- **极度重视最后 1% 的细节**：明确意识到「看似很小的表达偏差，可能导致思路偏移十万八千里」。会主动承认「方向没错，但细节表达有问题」，并立即修正。
- **自我纠错能力强**：在被指出「推过去」与「只做失效」矛盾后，能快速用自己的话重新表达正确版本，不依赖外部灌输。
- **喜欢先建立背景再追问机制**：先把「为什么需要配合」讲清楚，再追问「编译器具体如何生成屏障」。
- **倾向用「链路」思维**：习惯把写缓冲 → 本地 Cache → MESI 失效 → 读屏障顺序约束串成完整因果链，而不是孤立记点。
- **善于从已有结论引申新问题**：在确认屏障位置后，立即提出「写 + 强刷应作为整体具备原子性」的疑问。

## 当前学习状态

- 已能独立表达：读屏障的价值依赖写屏障配合；写端负责失效，读端只负责顺序。
- 对「编译器如何生成屏障」已有初步理解：把 volatile 看作开关，再根据实际是「读取」还是「更新」这个被修饰的变量，来决定用哪种屏障。
- 已进一步明确：编译器看的是编译后的机器指令（load / store），而不是源代码里的 `=` 或变量名。
- 对屏障位置已进一步表达：读屏障在前，保证读取顺序不会前置，读到的是前面更新过的最新值；写屏障在后，强制刷新 store buffer。
- 已打通：写屏障的作用就是保证 store buffer 内容与本地 cache 的一致，从而避免「store 以为成功了，但其他 local cache 没有被作废」的情况。
- 已能把整条链路收回最初图片：可见性 ← 写屏障；有序性 ← 读屏障；非原子性 ← 读+计算+写 中间可被其他线程插入。
- 当前进入 L03：指令重排序与 Happens-Before 规则。L01/L02 已确认清晰。
- 对指令重排序：已知其目的是优化执行顺序提高性能；在 volatile 场景下禁止重排。
- 对 Happens-Before：已接受官方定义；对 volatile 规则理解：先写后读必然读到最新值；先读后写则读到的是本地旧值，后续写无济于事。
- 已明确区分：Happens-Before 是规则，读写屏障是实现手段。
- 对传递性与程序次序：认为基于读写屏障编排，细节偏硬件暂不深挖。
- 计划：监视器锁规则单独作为专项学习。

## 引导建议（内部记录）

- 继续用「你先自己说」的方式，让用户把「写 + 强刷是否原子」的问题自己推一遍。
