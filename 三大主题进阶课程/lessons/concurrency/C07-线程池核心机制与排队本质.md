# C07 · 线程池：先 core，再进队列，满才开 max

> **今天只带走这一条**：任务提交到线程池，如果 core 线程已满，**不会立即创建新线程到 max，而是优先塞进阻塞队列排队**；只有队列塞满了且线程数 < max，才会开新线程救急；队列满了且已达 max，才触发拒绝策略。
> **用时**：15–20 分钟。

---

## 1. 原理

`ThreadPoolExecutor.execute(Runnable task)` 处理任务的严格三步走：

```
               提交任务
                  │
          当前线程数 < corePoolSize ?
             ├── 是 ──> 创建核心线程执行任务
             └── 否
                  │
          workQueue 阻塞队列能塞下 ?
             ├── 是 ──> 进入队列排队，等待空闲核心线程拉取
             └── 否
                  │
          当前线程数 < maximumPoolSize ?
             ├── 是 ──> 创建非核心线程执行该任务（救急）
             └── 否 ──> 触发 RejectedExecutionHandler 拒绝策略
```

### 底层核心机制：

1. **Worker 工作线程本质**：
   线程池里的线程被包装为 `Worker`，其核心就是死循环：
   ```java
   while ((task = getTask()) != null) { // 在 getTask() 里向阻塞队列拿任务
       task.run();                      // 执行业务逻辑，绝不是 start() 新线程
   }
   ```
2. **`ctl` 原子状态控制**：
   `AtomicInteger ctl` 用一个 32 位整型同时记录两件事：
   * **高 3 位**：线程池运行状态（`RUNNING`、`SHUTDOWN`、`STOP` 等）；
   * **低 29 位**：当前有效工作线程数 `workerCount`。
   借助 CAS 单次指令同时更新状态与线程数，无锁且绝对一致。

---

## 2. 误区

**「只要任务多了，线程池就会自动扩容到 maximumPoolSize。」**  
**大错！** 只要阻塞队列没塞满，线程池里的线程数永远不会超过 `corePoolSize`，哪怕还有几千个任务在队列里排队。

**「`Executors.newFixedThreadPool(10)` 是生产推荐的标准写法。」**  
**高危陷阱！** `newFixedThreadPool` 底层用的是 `new LinkedBlockingQueue<Runnable>()`（默认容量 `Integer.MAX_VALUE`，几乎无界）。当流量激增时，任务全部堆积在内存队列中，`maximumPoolSize` 和拒绝策略完全失效，最终直接导致 JVM **`java.lang.OutOfMemoryError: Java heap space`**。

## 3. 自检

1. **配置为 `core=2, max=10, queue=ArrayBlockingQueue(10)` 的线程池，连续提交 5 个耗时任务，此时活跃的工作线程数是多少？**
   *提示：前 2 个任务创建 2 个 core 线程，后 3 个任务全部进入队列排队，此时活跃线程数依然是 2，不会开启 max。*
2. **线程池里的核心线程执行完一个任务后，为什么不会立即销毁？**
   *提示：Worker 在 `getTask()` 中调用阻塞队列的 `take()`（或带超时时间的 `poll()`）进行阻塞等待，线程处于 WAITING 挂起状态，不占用 CPU，保持存活复用。*
