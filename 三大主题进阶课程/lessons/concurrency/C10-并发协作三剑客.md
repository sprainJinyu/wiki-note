# C10 · 协作三剑客：倒数、碰头与发牌

> **今天只带走这一条**：`CountDownLatch` 是**单向倒数到 0 唤醒等待者（一次性不可重置）**；`CyclicBarrier` 是**多线程互相等待到达栅栏（全到齐后一起冲破，可循环复用）**；`Semaphore` 是**可用许可证限流池（发牌与收牌）**。三者底层均基于 AQS 共享模式。
> **用时**：15–20 分钟。

---

## 1. 原理

### 三者核心模型与 AQS 落地对比

```
1. CountDownLatch(N)  ──>  [N] ➔ 倒数 count=0 ➔ 门闩打开，放行主线程 (不可复用)
2. CyclicBarrier(N)   ──>  线程 A ➔ 栅栏(等) ┐
                           线程 B ➔ 栅栏(等) ┼──> N 个全到齐 ➔ 冲破栅栏，可 reset() 复用
                           线程 C ➔ 栅栏(等) ┘
3. Semaphore(Permits) ──>  [ 许可池: 3 ] ➔ acquire() 扣减 ➔ release() 归还 (流量限流)
```

| 工具类 | 核心动词 | `state` 含义 | 是否可重用 | 经典业务场景 |
| :--- | :--- | :--- | :---: | :--- |
| **`CountDownLatch`** | `countDown()` / `await()` | 剩余倒数计数 | ❌ 否 | 主线程等待 3 个子任务并行查询全部完成 |
| **`CyclicBarrier`** | `await()` | 当前等待线程数（内含 Lock+Condition） | ✅ 是 | 多线程分片计算，全部到达阶段点后汇总并进入下一轮 |
| **`Semaphore`** | `acquire()` / `release()` | 剩余可用许可数 | ✅ 是 | 限制某个第三方 HTTP API 单机最大并发请求数为 10 |

---

## 2. 误区

**「`CountDownLatch` 倒数完毕后可以调用 reset 重复使用。」**  
**错误！** `CountDownLatch` 底层的 `state` 一旦通过 CAS 减到 0，就无法再重置。若需要多轮循环等待，必须使用 `CyclicBarrier`。

**「`Semaphore(1)` 和 `ReentrantLock` 没有任何区别。」**  
**大错！** `ReentrantLock` 是互斥独占锁，有明确的拥有者（只有加锁的线程才能解锁，支持重入）；而 `Semaphore` 没有线程所有权概念，线程 A `acquire()` 后，完全可以由线程 B 调用 `release()` 归还许可。

## 3. 自检

1. **主线程开启 5 个异步任务去拉取不同渠道的商品价格，主线程必须等 5 个结果全部返回后再比价，选哪个工具最轻量？**  
   *提示：`CountDownLatch(5)`，每个子任务执行完调用 `countDown()`，主线程 `await()`。*
2. **某个核心数据库单机最多只允许 20 个线程同时执行复杂报表查询，其他请求排队等待，选哪个？**  
   *提示：`Semaphore(20)`。*
