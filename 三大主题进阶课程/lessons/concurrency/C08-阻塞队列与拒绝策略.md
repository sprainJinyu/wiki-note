# C08 · 队列与拒绝：选错队列出事故，submit 默默吞异常

> **今天只带走这一条**：`SynchronousQueue` 是无容量的直接交接；`ArrayBlockingQueue` 是一把全局锁；`LinkedBlockingQueue` 是生产/消费双锁分离；`execute` 抛异常直接触发兜底处理，而 `submit` 会把异常静默封存在 `Future` 里，不调 `get()` 就永远看不见。
> **用时**：15–20 分钟。

---

## 1. 原理

### 一、 常见阻塞队列特性对比

| 阻塞队列 | 容量特性 | 锁实现机制 | 适用场景 / 风险点 |
| :--- | :--- | :--- | :--- |
| **`ArrayBlockingQueue`** | 构造必须指定固定有界容量 | 单把 `ReentrantLock`（生产与消费竞争同一把锁） | 内存占用低，吞吐中等，有界可控 |
| **`LinkedBlockingQueue`** | 默认 `Integer.MAX_VALUE`（极高危），可手动设界 | `putLock` 与 `takeLock` **双锁分离**（生产与消费互不阻塞） | 高吞吐；**生产必须显式指定容量**，严禁使用默认无界 |
| **`SynchronousQueue`** | 容量为 0（不存储元素） | 内部基于 AQS 转移节点直接交付 | 适合手递手快速处理的高并发短任务（如 `CachedThreadPool`） |

---

### 二、 4 种饱和拒绝策略

当 **队列塞满 且 工作线程达到 maximumPoolSize** 时触发：

```
1. AbortPolicy (默认)      ──> 直接抛出 RejectedExecutionException，阻断上游流程
2. CallerRunsPolicy        ──> 由「提交任务的调用者主线程」执行该任务（天然限流背压）
3. DiscardPolicy           ──> 静默丢弃该任务，不报错不抛异常（高危，慎用）
4. DiscardOldestPolicy     ──> 丢弃队列头部（最老）的一个任务，然后重新尝试提交当前任务
```

---

### 三、 `execute` vs `submit` 异常黑洞

```java
// 1. execute 方式：异常会抛出给当前 Worker 线程，默认打印在 stderr 并触发 UncaughtExceptionHandler
executor.execute(() -> {
    throw new RuntimeException("boom!"); // 控制台直接看得到报错
});

// 2. submit 方式：异常被包装在 FutureTask 内部，线程正常存活，不调 get() 异常被完全吞掉！
Future<?> future = executor.submit(() -> {
    throw new RuntimeException("silent boom!"); // 控制台没有任何动静！
});
// 必须显式 future.get() 才会抛出 ExecutionException
```

---

## 2. 误区

**「队列满了就一定会抛 `RejectedExecutionException` 导致请求报错。」**  
不一定！若配置为 `CallerRunsPolicy`，任务会退回给调用方主线程自己跑，既保证了任务不丢失，又天然拖慢了调用方的提交速率（形成优雅的负反馈背压）。

**「用 `submit()` 提交异步任务，代码报错了肯定能在日志里看到。」**  
**重大隐患！** `submit()` 内部会将 `Callable/Runnable` 包装为 `FutureTask`。执行出错时，它只是把 `Throwable` 赋值给内部的 `outcome` 属性并将状态置为 `EXCEPTIONAL`，绝不会主动打日志。如果不调 `future.get()`，线上报错如同石沉大海。

## 3. 自检

1. **为什么高并发生产-消费场景下 `LinkedBlockingQueue` 的吞吐量通常高于 `ArrayBlockingQueue`？**  
   *提示：`LinkedBlockingQueue` 采用 `putLock` 和 `takeLock` 双锁机制，生产者入队和消费者出队各持一把锁，互不干扰；而 `ArrayBlockingQueue` 入队和出队争抢同一把独占锁。*
2. **在处理非关键但量极大的异步日志刷新时，选用哪种拒绝策略最合适？处理核心扣款任务时呢？**  
   *提示：日志刷新可用 `DiscardPolicy` 或自定义告警丢弃；核心业务推荐 `CallerRunsPolicy` 或自定义持久化兜底，绝不能静默丢弃。*
