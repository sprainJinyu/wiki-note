# C14 · 弹性重试：退避抖动防雪崩，舱壁隔离保全局

> **今天只带走这一条**：自研重试组件（如 `retryable`）的核心是**指数退避（Exponential Backoff）+ 随机抖动（Full Jitter）**，防止所有重试请求在同一瞬间共振打垮下游；重试执行必须与**独立线程池隔离（Bulkhead 舱壁模式）**，严禁霸占业务主线程池，防止重试慢调用耗尽全局线程引发雪崩（场景 D）。
> **用时**：15–20 分钟。

---

## 1. 原理

### 一、 为什么必须「指数退避 + 随机抖动（Jitter）」？

```
固定间隔重试 (无抖动) ──> 流量尖峰：所有失败请求在 1s、2s、3s 整点同时发起 ──> 下游直接二次猝死！
指数退避 + Jitter    ──> 时间轴上均匀打散：Interval = min(Max, Base * 2^attempt) + random(0, Jitter)
```

```
重试请求数
  ▲
  │   ▲   ▲   ▲   (固定重试：形成巨大的脉冲尖峰)
  │  ─┼───┼───┼──────────
  │   ░▒▓▒░▒▓▒░▒▓ (加 Jitter：脉冲被削平为平缓波形)
  └────────────────────────► 时间 (s)
```

---

### 二、 舱壁隔离（Bulkhead）设计

```
[核心业务请求主线程池] ──── 正常调用 ────> [下游服务]
        │ (超时/瞬时失败)
        └── 提交重试任务 ───> [专用异步重试线程池 / 延时队列] ─── 异步退避重试 ──> [下游服务]
```

* **严禁在主调用线程中同步 `Thread.sleep()`**：否则 100 个并发慢重试瞬间耗尽 Tomcat 或业务线程池；
* **幂等性判定前置**：业务 4xx、参数校验、非幂等状态机变更坚决不重试（快速失败）；只针对网络超时、特定 502/503/504 进行有限次重试。

---

## 2. 误区

**「只要捕获到 Exception 就 `Thread.sleep(1000)` 循环重试 3 次，简单好用。」**  
**高危反模式！** 1. 同步 `sleep` 会霸占线程，高并发下迅速把线程池占满；2. 固定时间重试会引发多实例共振与重试风暴；3. 如果下游是数据库死锁或非幂等接口，盲目重试会引发数据错乱与雪崩。

**「重试次数越多越好，重试 10 次总能成功。」**  
**大错！** 超过 3 次的重试成功率呈断崖式下跌，反而会持续消耗系统 CPU、网络带宽与连接池。黄金法则：最多重试 2~3 次，失败立即进入死信队列（DLQ）或记录降级告警。

## 3. 自检

1. **在自研 `member-user-center` 的重试框架时，为什么不能共用主业务线程池来执行重试延时调度？**  
   *提示：避免重试任务堆积耗尽核心线程池资源，导致原本正常的非重试请求也无法处理，破坏系统整体可用性。*
2. **全随机抖动（Full Jitter）的核心数学思想是什么？**  
   *提示：在 `[0, min(Cap, Base * 2^attempt)]` 之间取随机数，让每一次重试在时间轴上实现完全均匀分布。*
