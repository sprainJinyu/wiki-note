# L02 · volatile：可见、有序，但不是原子

> **今天只带走这一条**：`volatile` 保证可见性与有序性，不保证 `count++` 这类复合操作的原子性。
> **用时**：15–20 分钟。读完能复述即可。下一张卡用 happens-before 把「可见」说精确。

---

## 1. 原理

对 `volatile` 变量：

* **可见**：一个线程的写，对随后读取这个变量的线程可见。
* **有序**：不能把这个变量的写，和它前面的普通写随便调换；也不能把这个变量的读，和它后面的普通读/写随便调换。
* **非原子**：`count++` 仍是读、加、写三步。两个线程可以都读到 0，都写成 1。

程序员记这三句就够。JMM 用内存屏障落实前两句，不必背屏障名字，只需知道量级：

| 操作 | 对重排的约束（直观） |
| :--- | :--- |
| volatile **写** | 写之前的普通写不能排到这次写之后；这次写与后面的读写之间有一条较重的屏障 |
| volatile **读** | 读之后的普通读/写不能排到这次读之前 |

硬件上，这通常表现为：写缓冲被刷走，其它核上的缓存行失效，下次读重新拿。**具体指令因 CPU 而异。** x86 上 JIT 曾经给 volatile 写配 `lock` 前缀（教材里常见 `lock addl $0x0,(%esp)`），那是实现片段，不是 Java 规范，ARM 等架构用别的 fence。通勤不要背那条汇编。

---

## 2. 误区

**「加了 volatile，多线程 `count++` 就安全。」**  
可见 ≠ 原子。计数要用 `AtomicInteger` 或锁。

**「双重检查单例的 `instance` 可以不加 volatile。」**  
`new` 不是一步：分配、写字段、把引用赋给 `instance` 可能被重排。另一个线程可能看到非 null 的引用，字段却还是默认值。`instance` 必须是 `volatile`，才能禁止这次发布被拆开看见。

---

## 3. 自检

1. **`volatile boolean ready` 赋值，和 `volatile int n; n++;`，哪个在多线程下是安全的写？**
   *提示：对 boolean 的写是单次写，可见性由 volatile 管；`n++` 是读改写，不管可见，结果仍会丢更新。*
2. **为什么不需要记住 `lock addl` 也能用对 volatile？**
   *提示：要记的是语言保证（可见、有序、非原子）。汇编是某一代 x86 JIT 的实现，换架构就变。*
