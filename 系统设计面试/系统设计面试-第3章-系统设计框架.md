# 第3章：系统设计面试框架

## 为什么要读这章？

这一章不教具体技术，教的是**一套可以复用的思考框架**——遇到一个模糊的问题时，怎么从"不知道从哪里下手"变成"有条理地拆解和分析"。这正好是你说的"抬头看"的操作方法。

---

## 核心：4 步框架

### 第1步：了解问题，界定范围（3-10 分钟）

**最重要的事情：问问题。** 不要一上来就画图，先搞清楚到底要做什么。

要搞清楚的事情：
- 要开发哪些功能？（不要什么都做）
- 用户量多大？增长预期如何？
- 技术栈有什么限制？
- 是创业公司级别的还是大厂级别的？

> 💡 **对你工作的启示**：接到新需求时，先问清楚"这个需求解决什么问题？边界在哪？"再开始想代码怎么写。

### 第2步：提出高层次设计并达成共识（10-15 分钟）

画一张框图，包含关键组件：
- 客户端 → API → Web 服务器 → 数据存储
- 辅助组件：缓存、CDN、消息队列

用具体用例走一遍流程，验证你的设计。**把对方当队友，一起讨论。**

> 💡 **对你工作的启示**：做设计前先在脑子里画一张"这个需求涉及哪些模块"的图，而不是直接打开 IDE 写代码。

### 第3步：深入设计（10-25 分钟）

在确定了整体蓝图后，选最关键的一个或多个组件深入。

- 跟对方确定：我们重点看哪块？
- 时间有限，不要每个组件都深入
- 和对方讨论取舍

### 第4步：总结（3-5 分钟）

不是"做完了"，而是：
- 找出系统的瓶颈在哪
- 讨论可能的优化方向
- 讨论出错情况（服务器挂了怎么办？）
- 讨论监控和运维

---

## 该做 vs 不该做

| ✅ 该做 | ❌ 不该做 |
|---------|----------|
| 问清楚再动手 | 没搞明白需求就开始画 |
| 先说整体，再说细节 | 一上来就深入某个组件 |
| 边想边说，让对方知道你在想什么 | 闷头自己想，沉默 |
| 提出多种方案对比 | 认准一个方案死磕 |
| 卡住了就请求提示 | 卡住了硬撑 |
| 承认设计有改进空间 | 说自己设计是完美的 |

## 📝 对你的实际用处

这个框架最大的价值不在面试，而是在你平时的工作中：

**下次接到商品卡需求时，试着按这个流程走一遍：**

```
① 搞清楚需求范围和边界（跟产品对清楚）
② 画一张简图：这个需求涉及哪些模块、数据怎么流转
③ 挑最复杂的那块深入想一下
④ 最后问自己：这个方案有什么瓶颈？哪里可能出问题？
```

**不用写长篇文档**，脑子里过一遍或者写个简单的提纲都行。关键是养成"先框架，后细节"的习惯。
