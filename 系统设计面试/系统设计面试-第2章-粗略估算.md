# 第2章：粗略估算

## 为什么要读这章？

这章不讲架构，讲的是**量级感**——当你看到一个需求时，能快速估算出"这个系统大概需要多少服务器、多大数据量"。没有量级感，你做的设计决策就是凭感觉。

**核心就一句话**：做设计决策前，先算一算扛不扛得住。

---

## 必须记住的 3 张表

### 1. 数据量单位（2 的幂）

| 缩写 | 全称 | 大小 |
|------|------|------|
| 1 KB | Kilobyte | 2^10 = ~1,000 bytes |
| 1 MB | Megabyte | 2^20 = ~1,000,000 bytes |
| 1 GB | Gigabyte | 2^30 = ~1,000,000,000 bytes |
| 1 TB | Terabyte | 2^40 |
| 1 PB | Petabyte | 2^50 |

### 2. 延迟数字（重要！）

| 操作 | 时间 |
|------|------|
| L1 缓存访问 | 0.5 ns |
| 分支预测错误 | 5 ns |
| L2 缓存访问 | 7 ns |
| 互斥锁 | 25 ns |
| 主存访问 | 100 ns |
| **压缩 1KB 数据 (Zippy)** | **3,000 ns = 3 μs** |
| 通过 1 Gbps 网络发送 2KB | 44 μs |
| SSD 随机读取 | 16 μs |
| **内存中顺序读取 1MB** | **250 μs** |
| 同一数据中心往返 | 500 μs |
| **SSD 顺序读取 1MB** | **1,000 μs = 1 ms** |
| 磁盘寻道 | 10 ms |
| **磁盘顺序读取 1MB** | **20 ms** |
| 发送数据包 CA→NL→CA | 150 ms |

**从中得出的结论**：
- 内存比磁盘快 **1000 倍** 以上
- 尽量**避免磁盘寻道**
- 压缩算法很快，传输前**先压缩**
- 数据中心跨区域发数据很耗时

### 3. 可用性数字

| 可用性 | 年停机时间 |
|--------|-----------|
| 99% (两个9) | ~3.65 天 |
| 99.9% (三个9) | ~8.77 小时 |
| 99.99% (四个9) | ~52.6 分钟 |
| 99.999% (五个9) | ~5.26 分钟 |

## 实际估算练习（Twitter 案例）

### 假设
- 月活 3 亿，50% 每天用
- 每人每天发 2 条推文
- 10% 的推文含媒体（图片/视频）

### 估算 QPS

```
DAU = 3亿 × 50% = 1.5亿
推文 QPS = 1.5亿 × 2条 / 24h / 3600s ≈ 3,500
峰值 QPS = 3,500 × 2 ≈ 7,000
```

### 估算存储

```
媒体大小 ≈ 1MB/条
每天媒体存储 = 1.5亿 × 2 × 10% × 1MB = 30TB/天
5年存储 = 30TB × 365 × 5 ≈ 55PB
```

> 💡 **注意**：估算是为了让你知道量级，不需要精确。关键是**过程**对不对。

## 估算小技巧

| 技巧 | 说明 |
|------|------|
| **四舍五入** | 99987/9.1 直接当成 100,000/10 |
| **记下假设** | 写下假设方便以后回顾 |
| **标上单位** | 写"5 MB"不要只写"5" |
| **常见估算题型** | QPS、峰值 QPS、存储、缓存、服务器数量 |

## 📝 对你有用的练习

下次做需求时，试着估算一下：

```
每天大概有多少请求？
每次请求返回多少数据？
一天下来要存多少数据？
现在的服务器能扛住吗？
```

不用算太细，有个量级就行。关键是**养成"先算一算"的习惯**。
