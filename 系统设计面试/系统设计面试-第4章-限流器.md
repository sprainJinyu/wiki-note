# 第4章：设计一个限流器

## 为什么要读这章？

限流器是后端开发**最常遇到的场景之一**——API 防刷、第三方接口保护、请求削峰。读这章能让你：

1. 理解几种常见的限流算法，以后做设计时能选对方法
2. 下次商品卡业务需要做 API 保护时，知道怎么设计

---

## 限流器的三个作用

- **防 DoS 攻击**：阻止恶意请求淹没你的服务器
- **控制成本**：减少不必要的服务器开销，控制第三方 API 调用费用
- **防止过载**：过滤机器人或用户的异常行为

---

## 5 种限流算法速览

| 算法 | 原理 | 优点 | 缺点 | 谁在用 |
|------|------|------|------|--------|
| **令牌桶** | 定期往桶里放令牌，请求消耗令牌 | 允许突发流量，易实现 | 参数调优有挑战 | Amazon, Stripe |
| **漏桶** | FIFO 队列，固定速率处理 | 流量平滑 | 突发流量堆积旧请求 | Shopify |
| **固定窗口** | 按时间段计数，超了就拒绝 | 内存高效，简单 | 窗口边界可能超限 | — |
| **滑动窗口日志** | 跟踪每个请求的时间戳，算精确计数 | 最精确 | 消耗内存 | — |
| **滑动窗口计数器** | 混合固定窗口 + 上一窗口重叠比例 | 平滑峰值，内存高效 | 近似值（误差<0.003%） | Cloudflare |

### 快速选择

- **要允许突发流量** → 令牌桶
- **要严格平滑流量** → 漏桶
- **要精确控制** → 滑动窗口日志
- **要均衡性能和精度** → 滑动窗口计数器
- **最简单的实现** → 固定窗口

---

## 限流器放在哪里？

| 位置 | 评价 |
|------|------|
| **客户端** | ❌ 不可靠，容易被篡改或忽略 |
| **服务器端** | ✅ 直接实现，可控 |
| **API 网关 / 中间件** | ✅ 独立组件，推荐用于微服务架构（如 AWS API Gateway） |

---

## 限流后的处理

超过限制时：

**HTTP 返回 429（Too Many Requests）**，并在响应头携带信息：

```
X-Ratelimit-Remaining: 0          // 还剩多少
X-Ratelimit-Limit: 100            // 窗口内允许几个
X-Ratelimit-Retry-After: 27       // 等多少秒再试
```

---

## 分布式环境下的挑战

| 问题 | 解决方案 |
|------|---------|
| **竞争条件** | 用 Redis 的 Lua 脚本或 Sorted Set 保证原子性 |
| **多台限流器同步** | 集中式数据存储（如 Redis）共享状态，不要用粘性会话 |
